# 存档系统改进方案

> 基于当前项目现状（存档系统/FacilityManager 为主要工作，事件中心/对象池/高亮为学习阶段），针对 Pipe 的删除/恢复/持久化场景，提供分层架构设计与数据流方案。

---

## 一、现状诊断：为什么代码越写越「屎山」？

### ❌ 核心问题：没有单一数据源 + 依赖方向混乱

```
Mouse_Touch
  ├─► HighlightSystem2（高亮）
  ├─► 自己维护 selectedobjs List
  ├─► 自己维护 resetobjs Stack（恢复用）
  └─► 自己调用 obj.SetActive(false)
                              ↓
FacilityManager
  ├─► 自己维护 progressData.facilities List
  ├─► 自己调用 SaveSystem
  └─► 自己管理 GLTFast 加载模型

PlayerData
  └─► 自己调用 SaveSystem
```

**问题表现：**
- 删除 pipe 时 `Mouse_Touch` 只 `SetActive(false)`，没告诉 `FacilityManager`
- `FacilityManager` 存了 `progress.json`，但不知道物体被删了
- 场景重载后已删的 pipe 又重新出现
- 想加一个新功能（比如删除音效）可能要改 3-4 个文件

### ❌ 核心缺失：GameObject ↔ FacilityData 的映射

代码中没有任何机制能通过 `GameObject` 找到对应的 `FacilityData`。当前只能靠名字匹配，脆弱且不可靠。

## 二、架构原理：分层设计与单向数据流

### 2.1 分层架构

```
┌───────────────────────────────────────────────────┐
│  Interaction Layer（交互层）                        │
│  Mouse_Touch —— 知道的越少越好                     │
│  职责：用户输入 → 调用 Manager 接口                 │
│  只认：FacilityIdentity.Id                         │
├───────────────────────────────────────────────────┤
│  Manager Layer（业务逻辑层 / 门面 Facade）           │
│  FacilityManager —— 所有操作的唯一入口               │
│  职责：增删改查、协调数据与表现、触发存档、广播事件    │
├───────────────────────────────────────────────────┤
│  Data Layer（数据层）                              │
│  FacilityData / ProgressData —— 纯数据结构         │
│  职责：描述设施状态（isDeleted 是最关键的字段）        │
├───────────────────────────────────────────────────┤
│  Persistence Layer（持久化层）                     │
│  SaveSystem —— 文件读写工具（已有，无需改动）        │
│  职责：JSON ↔ 磁盘                                 │
└───────────────────────────────────────────────────┘
```

### 2.2 核心规则

> **下层不知道上层的存在。**
> - `FacilityData` 不知道 `FacilityManager`
> - `FacilityManager` 不知道 `Mouse_Touch`
> - `SaveSystem` 不知道任何业务逻辑

### 2.3 单一数据源（Single Source of Truth）

> **永远只有一个地方存「这个 pipe 是否被删了」这一事实。**

| 数据 | 唯一来源 |
|------|---------|
| 某 pipe 是否被删除 | `FacilityData.isDeleted`（存于 progress.json） |
| 某 pipe 的位置 | `FacilityData.posX/Y/Z`（存于 progress.json） |
| 场景中 pipe 是否可见 | 由 `FacilityManager` 在加载时根据 `isDeleted` 决定 |

`GameObject.SetActive` 和 `Stack<GameObject>` 只是「表现层缓存」，**不是事实来源**。

## 三、关键组件设计

### 3.1 FacilityIdentity —— 身份绑定组件

**目的：** 每个 Pipe 的 GameObject 上挂一个不变的 ID，让代码可以在 O(1) 时间内找到对应的数据。

```
Pipe GameObject
  ├─ MeshRenderer
  ├─ MeshCollider
  └─ FacilityIdentity
       └─ id = "a7f3c2e1-4b8d-4f6c-9a2e-1d3b5c7f8a0c"  ← GUID，出生分配，一生不变
```

**设计要点：**
- `id` 用 `System.Guid.NewGuid().ToString()`，不用自增数字
  - 场景重载时自增会重复
  - GUID 在分布式/多场景中也不会冲突
- `id` 只在**第一次创建 Pipe 时分配一次**
  - 从 JSON 加载 Pipe 时直接读取已保存的 id，不重新分配
- 组件内部直接将 `gameObject.name = id`，方便调试

### 3.2 FacilityManager —— 统一操作入口

**职责清单：**
- 创建 Pipe → 生成 `FacilityData` + 实例化 GameObject + 分配 GUID
- 删除 Pipe → 设置 `isDeleted = true` + 存档 + 广播事件
- 恢复 Pipe → 设置 `isDeleted = false` + 存档 + 广播事件
- 加载场景 → 从 JSON 读取数据，只实例化 `isDeleted == false` 的设施

**关键改进点：**
- `GameObject` 实例化逻辑与数据操作逻辑在同一个类中，保证一致性
- 删除/恢复都**只改数据**，表现层通过事件被动更新
- 存档不再由各个脚本分散调用，全部在 Manager 内部决策

### 3.3 通信方式：C# 事件（发布-订阅）

**对比方案：**

| 方式 | 优点 | 缺点 |
|------|------|------|
| **C# event**（推荐） | 类型安全、轻量、直观 | 注意取消订阅防止内存泄漏 |
| **EventCenter**（已有） | 枚举管理模式统一 | 需要先在枚举中注册类型，略重 |
| **UnityEvent** | 可在 Inspector 拖拽 | 运行时调试不便 |
| 方法返回值 | 最简单直接 | 耦合度高，扩展难 |

**推荐方案：** 在 `FacilityManager` 中声明 C# 事件，各类关注者在 `OnEnable/OnDisable` 中订阅/取消。

```csharp
// FacilityManager 中定义事件
public event Action<string> OnFacilityDeleted;    // 参数 = 设施 ID
public event Action<string> OnFacilityRestored;   // 参数 = 设施 ID
public event Action<FacilityData> OnFacilityAdded; // 参数 = 设施数据
```

**为什么不是 EventCenter？**
- 你的 `EventCenter` 是全局单例，所有事件都堆积在 `GameEvent` 枚举里
- 随着项目增长枚举会越来越长
- C# `event` 是轻量级的观察者模式，更聚焦、类型安全

### 3.4 防抖自动保存（Debounced Auto Save）

**原理：** 不每次改动都立刻写磁盘（太频繁），而是标记「脏了」，然后启动一个短延迟（如 0.5 秒）。如果延迟期间又有新改动，重置计时器。延迟结束才真正写文件。

```
修改数据 → isDirty = true → 启动延迟计时器
                               │
                ┌──── 0.5 秒内有新修改？──→ 重置计时器
                │
                └──── 0.5 秒后无新修改 → 写入 JSON
```

**为什么这样设计：**
- 用户连续删除 5 个 pipe，只写一次磁盘，不是 5 次
- 退出场景时可以立即强制保存 `SaveNow()`
- 不依赖用户记住按保存键

## 四、完整交互流程

### 4.1 新建 Pipe（首次创建）

```
① 用户/系统调用 FacilityManager.CreateFacility(position, rotation)
    ↓
② FacilityManager：
   ├─ 创建 FacilityData
   │   ├─ id = Guid.NewGuid().ToString()
   │   ├─ posX/Y/Z = position
   │   ├─ rotX/Y/Z = rotation
   │   ├─ isDeleted = false
   │   └─ addedTime = DateTime.Now
   ├─ 加入 progressData.facilities
   ├─ 实例化 Pipe GameObject
   │   └─ 挂载 FacilityIdentity，AssignId(id)
   ├─ isDirty = true → 启动防抖自动保存
   └─ 广播 OnFacilityAdded(data)
```

### 4.2 选中 Pipe → 按 Delete 删除

```
① Mouse_Touch 左键点击
   ├─ 射线检测 → 获取 GameObject
   ├─ 获取 FacilityIdentity 组件 → identity.Id
   ├─ 高亮/取消高亮（HighlightSystem2）
   └─ 加入 selectedobjs 列表
        ↑ 不涉及任何数据操作，纯交互

② 按 Delete 键
   ├─ Mouse_Touch 调用 FacilityManager.Instance.DeleteFacility(identity.Id)
   │   ↑ 只传 ID，不传 GameObject
   │
   ├─ FacilityManager：
   │   ├─ 根据 ID 查找 FacilityData
   │   ├─ data.isDeleted = true
   │   ├─ isDirty = true → 防抖自动保存
   │   └─ 广播 OnFacilityDeleted(id)  ← 谁关心谁订阅
   │
   └─ Mouse_Touch（作为订阅者收到事件）
       ├─ selectedobjs 中移除此物体
       ├─ obj.SetActive(false)  ← 只是视觉效果
       └─ HighlightSystem2 移除高亮
```

### 4.3 按 R 恢复

```
① Mouse_Touch 检测到 R 键
   └─ 需要知道「上一个被删的是谁」
       └─ 方案见下方第五节的详细说明

② 调用 FacilityManager.Instance.RestoreFacility(id)
   ├─ data.isDeleted = false
   ├─ isDirty = true → 防抖自动保存
   └─ 广播 OnFacilityRestored(id)

③ Mouse_Touch 收到事件
   ├─ obj.SetActive(true)
   └─ 重新加入 selectedobjs（可选）
```

### 4.4 场景加载

```
① FacilityManager.Start()
   ├─ 从 progress.json 读取 ProgressData
   ├─ 遍历 facilities 列表
   │   ├─ 如果 isDeleted == true → 跳过，不生成
   │   └─ 如果 isDeleted == false → 实例化 Pipe 并挂载 FacilityIdentity
   └─ 场景中只出现「未被删除」的 Pipe
```

### 4.5 退出场景 / 自动保存触发

```
退出场景（OnApplicationQuit / OnDestroy）：
  ① FacilityManager 立即执行一次完整保存（跳过防抖延迟）

自动保存：
  ② 数据变更 → isDirty = true → 0.5 秒防抖 → 写入 progress.json
  ③ 任何时候调用 FacilityManager.Instance.SaveNow() 强制保存
```

## 五、关于「按 R 恢复」的两种方案

### 现状问题
当前 `Mouse_Touch` 用 `Stack<GameObject>` 保存被隐藏的物体。但这个 Stack 在场景重载后会丢失。改进方向应该以 JSON 中的数据为准，而非内存中的 Stack。

### 方案 A：简单方案（推荐起步）

**原理：** 在 `FacilityData` 中加一个 `deletedTime` 字段，按 R 时恢复**最近被删除的设施**，不区分是哪个物体。

```
按 R
  1. Mouse_Touch 调用 FacilityManager.Instance.RestoreLatest()
  2. FacilityManager 遍历 facilities
     ├─ 找到 isDeleted == true 且 deletedTime 最新的那个
     └─ 设置 isDeleted = false
  3. 存档 + 广播事件
```

✅ 实现简单，不需要 `Stack`
✅ 场景重载后也能正常工作（数据在 JSON 中）
❌ 如果场景中同时有多个 pipe 被删，用户不能精确选择恢复哪一个

### 方案 B：交互方案（更完整的体验）

**原理：** 被删的 pipe 依然保留一个「幽灵 GameObject」但处于隐藏状态，存储其 ID。R 键遍历所有隐藏物体，通过 FacilityIdentity 找到 id 并恢复。

```
按 Delete
  1. Mouse_Touch 调用 FacilityManager.DeleteFacility(id)
  2. FacilityManager 标记 isDeleted = true，存档
  3. Mouse_Touch 收到事件，不销毁 GameObject
     ├─ obj.SetActive(false)
     └─ 将 obj 放入一个局部 List（不是 Stack，且只存引用）

按 R
  1. Mouse_Touch 遍历隐藏列表
     ├─ 列表为空 → 尝试从最近的 Deleted 设施恢复（备选）
     └─ 列表非空 → Pop 栈顶，调用 FacilityManager 恢复
```

## 六、实现路线图（按复杂度排序）

### Phase 1：基础设施
- `FacilityData` 增加 `isDeleted` 和 `deletedTime` 字段
- 新建 `FacilityIdentity` 组件（取消注释并改造）
- 实例化 Pipe 时挂载 `FacilityIdentity`

### Phase 2：核心逻辑改造
- `FacilityManager` 增加 `DeleteFacility(id)` / `RestoreFacility(id)`
- `FacilityManager` 增加 C# 事件 `OnFacilityDeleted` / `OnFacilityRestored`
- `FacilityManager.LoadProgress()` 加载时跳过 `isDeleted == true` 的设施

### Phase 3：交互层适配
- `Mouse_Touch.DeleteKey` 不再直接操作对象，改为调用 Manager
- `Mouse_Touch` 订阅 Manager 事件，根据事件响应
- 移除 `resetobjs` Stack，改用基于 ID 的恢复逻辑

### Phase 4：优化
- 加入防抖自动保存
- 处理 `OnApplicationQuit` 时的强制保存
- 可选的：删除音效、UI 提示等扩展功能（通过订阅新事件，不改 Manager）

## 七、常见问题（FAQ）

### Q1：为什么一定要用 GUID 做 ID？用自增数字不行吗？

| 场景 | 自增数字 | GUID |
|------|---------|------|
| 单场景运行 | ✅ 正常 | ✅ 正常 |
| 重载场景 | ❌ 重置为 0，与 JSON 中已保存的 ID 冲突 | ✅ 无影响 |
| 多人协作或跨场景 | ❌ 可能重复 | ✅ 全球唯一 |
| 可读性 | ✅ 方便 | ❌ 一串乱码 |

**建议：** 不管项目大小，从一开始就用 GUID。Unity 的 `System.Guid.NewGuid().ToString()` 即可。

### Q2：`SetActive(false)` 后还能获取 `FacilityIdentity` 组件吗？

**能。** `SetActive(false)` 只禁用 GameObject 的 Update 和渲染，它的组件和 Transform 数据都还在。射线检测检测不到，但代码中 `GetComponent<FacilityIdentity>()` 可以正常调用。

但是 `Find` 或 `GetComponentInChildren` 在非活跃物体上会有问题。解决方案：**只通过 ID 查找，不通过 GameObject 查找**。

### Q3：为什么不能用场景中的 GameObject 数量来判断存档数据？

场景中的 GameObject 是暂时的（重载就销毁），JSON 数据是永久的。必须让 JSON 是真相来源。

### Q4：新的方案会破坏现有的 PlayerData 存档机制吗？

不会。`PlayerData` 存档的是玩家位置/旋转/摄像机状态，与 `FacilityManager` 的设施存档是**平行关系**，互不干扰。它们都使用 `SaveSystem` 工具类，但数据文件不同（`PlayerData.json` 和 `progress.json`）。

### Q5：`isDirty` 是什么？当前 FacilityManager 里没有啊。

**`isDirty` 是方案建议新增的，当前代码中没有。**

#### 什么是 Dirty Flag（脏标记）？

`isDirty` 是一个布尔变量，直译就是「是否脏了」，意思是 **「数据被修改过，和磁盘上的文件不一致了」**。

```csharp
private bool isDirty = false;
```

它的工作逻辑：

```
初始状态：isDirty = false（内存数据和 JSON 一致）
    │
用户删了一个 Pipe → data.isDeleted = true
    │
    └→ isDirty = true（内存数据和 JSON 不一致了，需要保存）
         │
         自动保存写入 JSON → isDirty = false（又一致了）
```

#### 为什么要加这个？

**避免频繁写磁盘。** 如果每次改一个数据都立刻 `File.WriteAllText`，用户连续删除 5 个 Pipe 就会写 5 次文件，没必要。用 `isDirty` 配合防抖，只在「数据真的变了且稳定下来后」才写。

#### 它和防抖（Debounce）是什么关系？

```
删除 Pipe → isDirty = true → 启动 0.5 秒计时器
                                  │
                   0.5 秒内又删了一个？→ 重置计时器（isDirty 保持 true）
                                  │
                   0.5 秒后没有新操作？→ 写入 JSON，isDirty = false
```

#### 具体代码长什么样

```csharp
public class FacilityManager : MonoBehaviour
{
    private bool isDirty = false;      // ← 新增
    private Coroutine autoSaveCoroutine; // 防抖协程

    // 外部调用
    public void SaveNow()
    {
        SaveProgress();           // 立即写文件
        isDirty = false;          // 重置标记
    }

    // 内部调用：防抖保存
    private void TryAutoSave()
    {
        isDirty = true;
        if (autoSaveCoroutine != null)
            StopCoroutine(autoSaveCoroutine);  // 重置计时器
        autoSaveCoroutine = StartCoroutine(AutoSaveRoutine());
    }

    private IEnumerator AutoSaveRoutine()
    {
        yield return new WaitForSeconds(0.5f);  // 等 0.5 秒
        if (isDirty)                            // 如果还是脏的
        {
            SaveProgress();
            isDirty = false;
        }
    }

    // 真正的存盘逻辑（已有，不用改）
    private void SaveProgress()
    {
        SaveSystem.SaveByJson(FILE_NAME, progressData);
    }
}
```

#### 一句话总结

> `isDirty` 只是一个**「有没有东西需要存」**的标记，配合防抖计时器避免频繁写文件。它和当前代码唯一的区别就是「当前每次 `AddFacility`/`RemoveFacility` 都立刻保存」，改为「标记脏了，等一会再批量保存」。

## 八、问题详解

### 8.1 关于 `CreateFacility` —— 这是新增还是已有？

**是新增的方法，但有现有的雏形。**

当前代码中创建 Pipe 的逻辑分散在两处：
- `FacilityManager.Start()` — 从 JSON 加载已有设施并实例化
- `Facilitied_test.cs` — 手动 `new FacilityData` + 调用 `AddFacility`

但是没有一个**统一的公开方法**能让人调用一句就完成「创建数据 + 实例化物体 + 分配 ID + 自动存档」这一整套流程。

`CreateFacility(position, rotation)` 就是把这个流程封装成一个方法：

```
// 外部只需调用这一句，其余所有事情 Manager 内部完成
FacilityManager.Instance.CreateFacility(new Vector3(10, 2, 5), Quaternion.identity);
```

它和 `AddFacility` 的关系是：`CreateFacility` 对外，`AddFacility` 对内。

| 方法 | 可见性 | 用途 |
|------|--------|------|
| `CreateFacility(pos, rot)` | `public` | 外部调用（交互层/测试脚本） |
| `AddFacility(FacilityData)` | `private` | `CreateFacility` 内部调用，加列表 + 存档 |
| `DeleteFacility(id)` | `public` | 外部调用 |
| `RestoreFacility(id)` | `public` | 外部调用 |

### 8.2 为什么用 C# 事件（event）？

#### 没有事件时的问题

假设你实现了 `FacilityManager.DeleteFacility(id)`，现在按 Delete 键时调用它。但删除之后除了改数据，你还想：

1. **隐藏 GameObject**（Mouse_Touch 的职责）
2. **移除高亮**（HighlightSystem2 的职责）
3. **播放删除音效**（未来可能加，AudioManager 的职责）
4. **更新 UI 计数**（未来可能加，UIManager 的职责）

**没有事件的做法：把 Manager 改成一坨：**

```csharp
// ❌ FacilityManager 需要知道所有下游模块
public bool DeleteFacility(string id)
{
    data.isDeleted = true;
    SaveNow();

    // 直接调用各个模块的方法
    mouseTouch.HideObject(id);          // 知道 Mouse_Touch
    highlightSystem.RemoveHighlight(id); // 知道 HighlightSystem
    audioManager.PlayDeleteSound();      // 知道 AudioManager
    uiManager.UpdateCount();             // 知道 UIManager

    return true;
}
```

每加一个新功能就要改 `FacilityManager`，且它知道的越来越多，违反了分层原则。

**用事件的做法：Manager 只广播，别人自己听：**

```csharp
// ✅ FacilityManager 只管发结果，不管谁在听
public bool DeleteFacility(string id)
{
    data.isDeleted = true;
    SaveNow();
    OnFacilityDeleted?.Invoke(id);  // 一句话广播，不关心谁订阅
    return true;
}
```

新增音效功能时：只需新建 `AudioManager` 自己订阅事件，**不用改一行 FacilityManager**。

```
FacilityManager 发出 OnFacilityDeleted
    ├─ Mouse_Touch 收到 → 隐藏物体、清除高亮
    ├─ AudioManager 收到 → 播放音效          ← 新加，不需要改 Manager
    └─ UIManager 收到 → 更新计数              ← 新加，不需要改 Manager
```

#### 事件的核心好处

| 角度 | 说明 |
|------|------|
| **解耦** | 事件的发布者不需要知道谁在听，监听者不需要知道谁发的 |
| **可扩展** | 加新功能只需加新监听者，不改现有代码（开闭原则）|
| **可拆卸** | 监听者 `OnDisable` 取消订阅，不影响其他模块 |
| **聚焦** | C# event 是类级别的，比全局 EventCenter 的枚举更轻量和精确 |

#### 什么时候不用事件

- **简单的一对一调用**（比如 A 调用 B 的一个方法）→ 直接调用即可，不需要事件
- **数据需要返回值** → 用方法返回值，不用事件

```
直接调用（不需要事件）          需要事件（一对多解耦）
  A → B.Method()               A → 广播
                                 ├─ B 响应
                                 ├─ C 响应
                                 └─ D 响应
```

### 8.3 事件在你的项目里怎么用（具体到代码）

#### Step 1：在 FacilityManager 中声明事件

```csharp
public class FacilityManager : MonoBehaviour
{
    // 声明事件（和属性同一级别）
    public event Action<string> OnFacilityDeleted;   // 参数：设施 ID
    public event Action<string> OnFacilityRestored;  // 参数：设施 ID
    public event Action<FacilityData> OnFacilityAdded; // 参数：设施数据

    public bool DeleteFacility(string id)
    {
        FacilityData data = progressData.facilities.Find(f => f.id == id);
        if (data == null || data.isDeleted) return false;

        data.isDeleted = true;
        isDirty = true;
        TryAutoSave();   // 防抖自动保存

        OnFacilityDeleted?.Invoke(id);  // ✅ 广播事件

        return true;
    }
}
```

#### Step 3：关于「恢复时怎么找到被隐藏的物体」

这是关键问题。`SetActive(false)` 后无法被射线检测到，所以需要**提前存好 ID → GameObject 的映射**。

**简单方案**：在 Mouse_Touch 维护一个 `Dictionary<string, GameObject>`

```csharp
public class Mouse_Touch : MonoBehaviour
{
    private Dictionary<string, GameObject> hiddenObjects = new Dictionary<string, GameObject>();

    private void OnFacilityDeletedHandler(string id)
    {
        GameObject obj = selectedobjs.Find(o =>
            o.GetComponent<FacilityIdentity>()?.Id == id);
        if (obj != null)
        {
            hiddenObjects[id] = obj;   // 存起来供恢复用
            obj.SetActive(false);
            HighlightSystem2.Instance.RemoveHighlight(obj);
            selectedobjs.Remove(obj);
        }
    }

    // 按 R 恢复
    private void Update()
    {
        if (Input.GetKeyDown(KeyCode.R))
        {
            // 从最近的被删设施恢复
            string recentId = FacilityManager.Instance.GetRecentDeletedFacilityId();
            if (recentId != null && hiddenObjects.TryGetValue(recentId, out GameObject obj))
            {
                FacilityManager.Instance.RestoreFacility(recentId);
                // 恢复操作会在事件处理函数中完成
            }
        }
    }

    private void OnFacilityRestoredHandler(string id)
    {
        if (hiddenObjects.TryGetValue(id, out GameObject obj))
        {
            obj.SetActive(true);
            hiddenObjects.Remove(id);
            selectedobjs.Add(obj);          // 重新加入选中列表
            HighlightSystem2.Instance.EnableHightlight(obj, Color.Lerp(Color.red, Color.yellow, 0.5f), 10f);
        }
    }
}
```

#### 事件订阅/取消的「三要三不要」

| ✅ 要 | ❌ 不要 |
|------|--------|
| 在 `OnEnable` 订阅 | 在 `Awake` 或 `Start` 订阅不取消 |
| 在 `OnDisable` 取消订阅 | 依赖 `OnDestroy` 取消（物体不销毁就不执行） |
| 取消前判空 `if (Instance != null)` | 使用 `Find` 或 `FindObjectOfType` 获取发布者 |

### 8.4 C# event 和 EventCenter 怎么选

| | C# event | EventCenter（你写的） |
|--|----------|---------------------|
| 定义位置 | 在发布者类中声明 | 在全局枚举中注册 |
| 作用域 | 仅发布者内部可知 | 全局可见 |
| 参数类型 | 类型安全（`Action<string>`） | 泛型强转 |
| 耦合度 | 需要拿到发布者实例 | 全局单例，不需要发布者引用 |
| 适合场景 | 模块内部通信 | 跨模块、跨场景通信 |

**建议：** 对于 FacilityManager 和 Mouse_Touch/HighlightSystem 之间的通信，用 C# `event` 就够了。不需要用到全局 EventCenter。

## 九、总结

| 当前问题 | 改进方案 |
|---------|---------|
| 删除 pipe 只藏了 GameObject | 删除 = `isDeleted = true`，以 JSON 数据为准 |
| 场景重载后已删 pipe 又出现 | 加载时跳过 `isDeleted == true` 的设施 |
| 无法定位 GameObject 对应的数据 | 挂载 `FacilityIdentity`，用 GUID 关联 |
| Mouse_Touch 自己管恢复栈 | 移除 Stack，改为通过 ID 向 Manager 查询 |
| 多个脚本各自调用 SaveSystem | 写操作集中到 FacilityManager 统一管理 |
| 改一个功能要改 N 个文件 | C# 事件解耦——管理者只管发结果，谁关心谁订阅 |
| 用户要手动按保存键 | 防抖自动保存 + 退出时强制保存 |
