## Q1：为什么 OnEnable 订阅事件会报 NullReferenceException？

### 错误信息

```
NullReferenceException: Object reference not set to an instance of an object
Mouse_Touch.OnEnable () (at Assets/Scripts/HighLight/Mouse_Touch.cs:19)
```

第 19 行代码：

```csharp
private void OnEnable()
{
    FacilityManager.Instance.OnFacilityDeleted += OnFacilityDeletedHandler;
}
```

### 原因

**`FacilityManager.Instance` 是 `null`。** 因为 Unity 脚本的执行顺序问题：

```
场景加载
  │
  ├─ 物体 A 的 Awake()    ← 可能先执行
  ├─ 物体 B 的 Awake()    ← 可能后执行
  │        ↑ 不保证先后顺序！
  ├─ 物体 A 的 OnEnable() ← 紧跟着它的 Awake
  ├─ 物体 B 的 OnEnable() ← 紧跟着它的 Awake
  │
  └─ 所有物体的 Start()   ← 在所有 Awake 和 OnEnable 都完成后才执行
```

如果 `Mouse_Touch` 的物体比 `FacilityManager` 的物体先被 Unity 唤醒，则 `FacilityManager` 的 `Awake()` 还没运行，`Instance` 尚未赋值，此时 `Mouse_Touch.OnEnable()` 中访问 `FacilityManager.Instance` 就是 `null`。

### 原理：Unity 的 Awake → OnEnable → Start 顺序

| 阶段 | 特点 |
|------|------|
| `Awake()` | 场景中所有物体的 `Awake` 同时触发，**不保证先后** |
| `OnEnable()` | 紧随所属物体的 `Awake` 触发，同样**不保证先后** |
| `Start()` | 在所有 `Awake` 和 `OnEnable` **全部执行完毕后**，才逐个执行 |

所以结论是：**`Awake` 和 `OnEnable` 中访问其他单例是不安全的，因为无法保证那个单例的 `Awake` 已经跑完。**

### 解决方案

**把订阅从 `OnEnable` 移到 `Start`：**

```csharp
void Start()
{
    // Start 执行时，所有 Awake 都已跑完
    // Instance 一定不为 null
    FacilityManager.Instance.OnFacilityDeleted += OnFacilityDeletedHandler;
}
void OnDestroy()
{
    // Start 订阅 → OnDestroy 取消
    if (FacilityManager.Instance != null)
        FacilityManager.Instance.OnFacilityDeleted -= OnFacilityDeletedHandler;
}
```

### 为什么 Start 是安全的？

Unity 的执行保证：

```
所有 Awake() 全部完成
      ↓
所有 OnEnable() 全部完成
      ↓
第一个 Start() 开始执行  ← 到这里时，所有单例的 Instance 都就绪了
```

### 附加：订阅/取消的配对原则

| 在哪里订阅 | 就在哪里取消 |
|-----------|-------------|
| `Awake()` | `OnDestroy()` |
| `OnEnable()` | `OnDisable()` |
| `Start()` | `OnDestroy()` |

`OnEnable/OnDisable` 配对适合物体频繁激活/失活的场景，`Start/OnDestroy` 配对适合一次性订阅。

## Q2：事件订阅是「自己调自己」吗？

### 问题描述

```
Mouse_Touch 调用 DeleteFacility(id)
  → DeleteFacility 内部触发 OnFacilityDeleted 事件
    → 又调回 Mouse_Touch 的 OnFacilityDeletedHandler
这是不是自己调自己？
```

### 答案：不是。

`DeleteFacility` 和 `OnFacilityDeleted` 是两个不同的东西：

| 名称 | 类型 | 时态 | 职责 |
|------|------|------|------|
| `DeleteFacility(id)` | **方法** | 命令式 | 改数据 + 存档 |
| `OnFacilityDeleted` | **事件** | 过去式 | 通知表现层更新 |

### 执行流程

```
Mouse_Touch
  │
  ├─① 调用 FacilityManager.DeleteFacility(id)
  │     │
  │     └─ FacilityManager 内部：
  │          ├─ data.isDeleted = true    ← 改数据（Manager 的职责）
  │          ├─ TryAutoSave()            ← 存档（Manager 的职责）
  │          └─ OnFacilityDeleted?.Invoke(id) ← ② 广播通知（Manager 的职责）
  │
  ├─③ 事件 OnFacilityDeleted 触发
  │     │
  │     └─ Mouse_Touch.OnFacilityDeletedHandler(id) ← 收到通知
  │          ├─ hiddenObjects[id] = obj  ← 存引用
  │          ├─ obj.SetActive(false)     ← 隐藏物体（Mouse_Touch 的职责）
  │          └─ selectedobjs.Remove(obj) ← 移出列表（Mouse_Touch 的职责）
```

**关键：** 步骤 ① 和步骤 ③ 是**前后衔接的两个步骤**，职责不同：

- ① 是**下命令**（改数据、存档）
- ③ 是**收到命令执行结果后做自己的事**（更新画面）

### 为什么非要用事件？

不用事件时，Manager 需要知道所有下游模块：

```csharp
// ❌ 不用事件：Manager 什么都管
public bool DeleteFacility(string id)
{
    data.isDeleted = true;
    TryAutoSave();
    mouseTouch.HideObject(id);          // 知道 Mouse_Touch
    highlightSystem.RemoveHighlight(id); // 知道 HighlightSystem
    audioManager.PlayDeleteSound();      // 知道 AudioManager
    // 加一个功能就要改这里
}
```

用事件后：

```csharp
// ✅ 用事件：Manager 只发结果
public bool DeleteFacility(string id)
{
    data.isDeleted = true;
    TryAutoSave();
    OnFacilityDeleted?.Invoke(id);  // 一句话，不关心谁在听
}
```

**增加新功能（如删除音效）时不需要改 Manager 一行代码。**

### 一句话总结

> 你不是在「自己调自己」——你是在**做完事后喊一声"完事了"**，关心这件事的人（Mouse_Touch、AudioManager 等）各自响应。发布者不关心谁在听，监听者不关心谁发的。

## Q3：为什么 object 不自动消失？

### 问题描述

按 Delete 键后 JSON 数据确实更新了（`isDeleted = true`），但物体没有立即隐藏，重开场景后才隐藏。

### 原因

`DeleteOrHideSelectedObject()` 中混用了**新旧两套逻辑**，互相干扰：

```csharp
private void DeleteOrHideSelectedObject()
{
    // ... 遍历 selectedobjs ...
    FacilityIdentity identity = obj.GetComponent<FacilityIdentity>();
    if(identity != null)
    {
        FacilityManager.Instance.DeleteFacility(identity.Id);
        // ↑ 这里触发了事件，事件处理函数已经执行了隐藏操作
    }

    obj.SetActive(false);              // ❌ 旧代码残留：重复隐藏
    resetobjs.Push(obj);               // ❌ 旧代码残留：往旧 Stack 里塞
    HighlightSystem2.Instance.RemoveHighlight(obj); // ❌ 旧代码残留：重复清高亮
    // ...
    selectedobjs.Clear();              // ❌ 旧代码残留：列表已被事件处理逐个移除
}
```

**关键问题：** 由于 Unity 的事件是**同步触发**的，`DeleteFacility` 调用后，`OnFacilityDeletedHandler` 立即执行完毕（隐藏了物体），但旧代码接着又跑了一遍，导致行为混乱。

### 正确的执行流程（只用新逻辑）

```
DeleteOrHideSelectedObject()
  └─ 遍历 selectedobjs
       └─ 获取 FacilityIdentity.Id
            └─ 调用 Manager.DeleteFacility(id)
                 │
                 └─ OnFacilityDeleted 事件触发
                      └─ OnFacilityDeletedHandler 执行：
                           ├─ hiddenObjects[id] = obj
                           ├─ obj.SetActive(false)
                           ├─ RemoveHighlight(obj)
                           └─ selectedobjs.Remove(obj)
                 
                 控制返回，不需要做任何额外操作
```

### 解决方案

去掉 `DeleteOrHideSelectedObject()` 中 `DeleteFacility` 调用之后的所有旧代码：

- 去掉 `obj.SetActive(false)`—事件已处理
- 去掉 `resetobjs.Push(obj)`—旧的 Stack 不再需要
- 去掉 `RemoveHighlight(obj)`—事件已处理
- 去掉 `selectedobjs.Clear()`—事件已逐个移除

### 教训

**两套逻辑同时运行 = 混乱。** 新旧切换时，要么全改，要么留一个过渡期测试，不要新旧混在一个方法里。
